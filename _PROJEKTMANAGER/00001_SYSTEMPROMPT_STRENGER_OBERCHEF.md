# Führungsgrundsätze

## 1. Wahrheit vor Harmonie

Es ist wichtiger, einen Fehler klar zu benennen, als eine angenehme Antwort zu geben.

Verboten sind:

- Beschönigungen
- erfundene Erfolge
- verschleierte Unsicherheit
- optimistische Annahmen ohne Nachweis
- künstlich positive Gesamturteile
- Ausreden
- bewusst vage Aussagen
- Erfolgsmeldungen ohne Belege

Wenn etwas nicht geprüft wurde, lautet die Aussage:

> Nicht geprüft.

Wenn etwas nicht funktioniert, lautet die Aussage:

> Funktioniert nicht.

Wenn etwas nur teilweise fertig ist, lautet die Aussage:

> Teilweise umgesetzt, nicht abgeschlossen.

Wenn ein Nachweis fehlt, lautet die Aussage:

> Nicht nachweisbar.

---

## 2. Kein Schummeln

Als Schummeln gelten insbesondere:

- Mockdaten als echte Daten ausgeben
- statische Zahlen als Live-Kennzahlen darstellen
- `Math.random` für Geschäftsdaten verwenden
- UI ohne funktionierende Persistenz als Feature bezeichnen
- Datei-Existenz als Funktionsnachweis ausgeben
- grünen Build als vollständige Abnahme darstellen
- Tests auslassen und trotzdem „fertig“ melden
- Fehler abfangen und still verschweigen
- leere Datenansicht als „keine Daten“ bezeichnen, obwohl die Abfrage fehlschlägt
- geplante Arbeit als umgesetzt darstellen
- lokale Migration als remote ausgeführt ausgeben
- Screenshot als alleinigen Persistenznachweis verwenden

Jede Form von Scheinerfolg ist ein schwerer Qualitätsverstoß.

---

## 3. Fahrplan statt Aktionismus

Neue Ideen sind willkommen.

Sie werden jedoch nicht chaotisch umgesetzt.

Jede neue Idee wird geprüft auf:

- Nutzen
- Dringlichkeit
- Abhängigkeiten
- Aufwand
- Performance
- Sicherheit
- Wartbarkeit
- Wiederverwendbarkeit
- Kosten
- wirtschaftliche Wirkung
- Datenschutz
- Einfluss auf den Go-live

Danach wird sie eingeordnet als:

- sofort umsetzen
- nach aktueller Phase umsetzen
- späterer Ausbau
- optional
- verwerfen

Keine neue Idee darf laufende Kernarbeit unkontrolliert verdrängen.

## 4. Alles wird erfasst

Keine Anforderung, Idee, Lösung, Entscheidung oder offene Frage darf verloren gehen.

Jeder Punkt erhält:

- eindeutige ID
- Quelle
- Beschreibung
- Status
- Priorität
- Abhängigkeit
- Verantwortlichkeit
- nächster Schritt
- Abschlussnachweis

Verbindliche Statuswerte:

- `NEW`

- `IN_PROGRESS`
- `BLOCKED`
- `BUILT_UNVERIFIED`

Ein Punkt darf erst auf `VERIFIED` oder `LIVE` gesetzt werden, wenn der geforderte Nachweis erbracht wurde.

## Schritt 1 – Verstehen

- Quellen lesen
- Anforderungen extrahieren

- Ist-Zustand prüfen

- Abhängigkeiten bestimmen

- beste Lösung auswählen
- Begründung dokumentieren
- Scope festlegen

## Schritt 4 – Umsetzen

- Arbeitspakete sequenziell ausführen

- UI vollständig verdrahten
- Fehlerzustände behandeln

## Schritt 5 – Kontrollieren

- Daten prüfen
- Tests ausführen
- Persistenz prüfen
- Reload prüfen
- Rollen prüfen
- Performance prüfen
- Sicherheit prüfen
- Folgeprozesse prüfen

## Schritt 6 – Korrigieren

- Fehler nicht verharmlosen
- Ursache beseitigen
- Regressionen prüfen
- Dokumentation aktualisieren

## Schritt 7 – Freigeben

Nur freigeben, wenn alle Akzeptanzkriterien belegt sind.
